## What this package does

This package gives the Mirte robot a reliable answer to the question *"where am I?"* It fuses four sources of pose information — AMCL (laser-based localisation on a pre-built map), an EKF (sensor fusion of wheel odometry and IMU), AprilTag landmark corrections (re-seeding AMCL when a known tag is spotted), and optionally RTAB-Map (visual SLAM) — into a single `/robot_pose` topic that the rest of the system can consume.

The high-level pipeline is:

```
/scan (lidar) ──────────────────────────────► AMCL ───────────────────────►┐
                                               ▲                            │
/mirte_base_controller/odom ──► EKF ──► /odometry/filtered ────────────────►┤
/io/imu/movement/data ────────►                                             │
                                                                            │
semantic_map.yaml ──► AprilTagCorrector ──► /initialpose ──► AMCL (reseed) │
camera TF (apriltag_ros) ──────►                                            │
                                                                            │
/camera/* (depth + RGB) ────────────────────► RTAB-Map (optional) ─────────►┤
                                                                            │
                                                              HybridLocaliser
                                                                    │
                                                                    ▼
                                                             /robot_pose
```

## The map

### What an occupancy grid is

AMCL needs a 2-D floor plan of the environment loaded into memory before it can do anything. ROS represents this as an **occupancy grid** — a grayscale PNG or PGM image where:

- **White (255)** = free space the robot can drive through
- **Black (0)** = occupied / wall
- **Grey (128-ish)** = unknown

The image is paired with a YAML file that tells the map server how to convert pixels into real-world metres.

### test_map.yaml

```yaml
image:           test_map.pgm   # the image file (relative path)
resolution:      0.05           # 1 pixel = 5 cm
origin:          [-2.5, -1.5, 0.0]   # real-world coords of the bottom-left pixel
occupied_thresh: 0.65           # pixel brightness above this = occupied
free_thresh:     0.196          # pixel brightness below this = free
negate:          0              # 0 = white is free, 1 = invert
```

**origin** is a `[x, y, yaw]` triple. It pins the image into the map coordinate frame. Our map is 5 m × 3 m (100 × 60 pixels at 0.05 m/px), so we set origin to `(-2.5, -1.5)` to put (0,0) at the centre of the room.

### test_map.pgm

The map was generated by `generate_map.py`. It contains:
- Outer walls (3 px border)
- Station 1 (left, columns 5–20): the unsorted component pickup zone
- Station 2 (right, columns 80–95): the sorting dropoff boxes

This is a **test/placeholder map**. For a real deployment, capture a map with `nav2_map_server`'s `map_saver_cli` after running `slam_toolbox` or `cartographer` while driving the robot around manually.

## AMCL — Adaptive Monte Carlo Localisation

### The idea

AMCL is a probabilistic algorithm that answers: *given a map and a laser scan, what is the most likely pose of the robot?*

It maintains a cloud of **particles** — each particle is a hypothesis: "maybe the robot is at (x, y, θ)." At startup the particles are spread over the whole map. Each time:

1. The robot moves → particles are spread according to the **motion model** (how uncertain the wheels are)
2. A new laser scan arrives → particles that predict a scan close to what was actually measured are **reweighted upward**; those that are inconsistent are **reweighted downward**
3. The particle cloud **resamples** — bad hypotheses die, good ones clone → the cloud converges around the true pose

The result is published as `/amcl_pose` (`PoseWithCovarianceStamped`) — a pose *and* a 6×6 covariance matrix describing how confident the estimate is.

"Adaptive" refers to **KLD-sampling** (Kullback–Leibler Divergence sampling): the number of particles automatically increases when the pose is uncertain (robot just started, or got kidnapped) and shrinks when the pose is well-known. This keeps computation proportional to the actual difficulty of the problem.

### How we got it working

AMCL in ROS2 nav2 is a **lifecycle node**. That means it goes through explicit states:

```
Unconfigured → Configured → Active → (publishing /amcl_pose)
```

It does *not* start publishing anything until it reaches `Active`. The `nav2_lifecycle_manager` automates this transition — it configures and activates `map_server` and `amcl` in order, then keeps them alive.

The critical dependency chain is:

1. `map_server` must be Active and `/map` must be published before AMCL configures
2. AMCL must receive an initial pose estimate (via `/initialpose`) before its particle filter converges
3. Our `localisation_input_node` waits for `/map` to appear, then fires a `PoseWithCovarianceStamped` on `/initialpose`
4. AMCL seeds its particle cloud from that initial pose and begins localising

**Bug that was blocking this:** `amcl_config.yaml` had `initial_pose_a: 0.0cd ~` — a terminal command (`cd ~`) had accidentally been pasted into the YAML. YAML parsed this as a string value instead of a float, causing AMCL's parameter server to reject the config and crash before the lifecycle manager could activate it. Fixed to `initial_pose_a: 0.0`.

**Second bug that was silently dropping all /amcl_pose messages:** nav2_amcl publishes `/amcl_pose` with QoS `RELIABLE + TRANSIENT_LOCAL` (the ROS2 equivalent of a "latched" topic). Subscribers must use the *same* durability policy — a `VOLATILE` subscriber simply receives nothing from a `TRANSIENT_LOCAL` publisher. Both `localisation_output_node.py` and `hybrid_localiser.py` were subscribing with the default QoS (VOLATILE). Fixed by adding an explicit `QoSProfile(durability=TRANSIENT_LOCAL, reliability=RELIABLE)` to those subscriptions.

### amcl_config.yaml — parameter-by-parameter

```yaml
amcl:
  ros__parameters:
```

The `amcl:` / `ros__parameters:` nesting is required by the ROS2 parameter file convention. Parameters are namespaced under the node name.

#### Particle filter

| Parameter | Value | Why |
|-----------|-------|-----|
| `min_particles` | 1000 | Floor on particle count. Even when very confident, keep 1000 particles so a sudden change in environment doesn't leave us with too few hypotheses. |
| `max_particles` | 5000 | Ceiling on particle count. Mirte's Raspberry Pi 4 can handle 5000 particles at ~5 Hz comfortably. Going to 10000 starts lagging. |

#### Update thresholds

| Parameter | Value | Why |
|-----------|-------|-----|
| `update_min_d` | 0.05 m | Only reprocess a new scan if the robot has moved at least 5 cm since the last update. Prevents wasting CPU reprocessing scans while stationary. |
| `update_min_a` | 0.05 rad (~3°) | Same idea for rotation. Ignore scan updates when barely turning. |

#### Laser / sensor model

| Parameter | Value | Why |
|-----------|-------|-----|
| `laser_min_range` | 0.15 m | Ignore returns closer than 15 cm — at this distance the lidar often picks up the robot's own body or mounting hardware. |
| `laser_max_range` | 16.0 m | Maximum reliable range of the lidar. Points beyond this are ignored. |
| `max_beams` | 60 | Only use 60 evenly-spaced beams per scan even if the lidar gives 360. More beams = more accuracy but more CPU. 60 is a good balance for a slow ARM processor. |
| `laser_model_type` | `likelihood_field_prob` | See below. |

**laser_model_type choices:**

- `likelihood_field` — fast, standard. Each beam's expected distance is looked up in a pre-computed distance field of the map. No raycasting needed.
- `likelihood_field_prob` — same algorithm but uses a probabilistic mixture that handles random noise better. Chosen because Mirte's lidar has occasional phantom readings.
- `beam` — full physical beam model with raycasting. Most accurate but 10× slower — too slow for Mirte's ARM CPU.
- `gompertz` — a variant not well documented in nav2; avoided.

#### Z-weights (mixture model)

| Parameter | Value | Why |
|-----------|-------|-----|
| `z_hit` | 0.8 | 80% of a beam's likelihood is explained by a real nearby wall (Gaussian around expected range). |
| `z_rand` | 0.2 | 20% is explained by random noise / glass / reflections. These two must sum to ≤ 1.0. |
| `sigma_hit` | 0.1 m | Standard deviation of the Gaussian for the "hit" component — how much range error is allowed before a beam is considered not to match a wall. 10 cm is reasonable for a budget lidar. |

#### Recovery

| Parameter | Value | Why |
|-----------|-------|-----|
| `recovery_alpha_slow` | 0.001 | Long-term average weight of particles. Very slow to react — essentially tracks "how good are we doing overall." |
| `recovery_alpha_fast` | 0.1 | Short-term average. If the fast average drops much lower than the slow average, AMCL injects random particles across the map to recover from a kidnapped-robot scenario. Low `alpha_slow` makes recovery rare and deliberate — avoids false recovery scattering on Mirte's noisy lidar. |

#### Coordinate frames

| Parameter | Value | Why |
|-----------|-------|-----|
| `global_frame_id` | `map` | The fixed world frame. The map is defined in this frame. |
| `odom_frame_id` | `odom` | The frame published by wheel odometry / EKF — continuous but drifts. |
| `base_frame_id` | `base_link` | The robot's body centre. |
| `transform_tolerance` | 3.0 s | How stale a TF transform can be before AMCL complains. Set high (3 s) because Mirte's ARM sometimes has latency spikes, and a tight tolerance causes false "TF timeout" errors that kill localisation. |

#### Initial pose

| Parameter | Value | Why |
|-----------|-------|-----|
| `initial_pose_x` | 0.0 | Robot starts at the map origin in X. |
| `initial_pose_y` | 0.0 | Robot starts at the map origin in Y. |
| `initial_pose_a` | 0.0 | Robot starts facing the positive-X direction (0 radians = east). |

These only take effect if `set_initial_pose: true` is set, otherwise AMCL waits for the `/initialpose` topic. We use the input node approach (see below) so these are a secondary fallback.

#### Scan topic

| Parameter | Value | Why |
|-----------|-------|-----|
| `scan_topic` | `/scan` | The topic name AMCL subscribes to for laser data. Mirte's lidar publishes here by default. |

## EKF — Extended Kalman Filter (robot_localization)

### The idea

Wheel odometry alone is unreliable over time — small errors in wheel radius or ground contact accumulate into large drift. The IMU provides angular rate and acceleration but drifts on yaw over time. Neither is good enough alone.

An **Extended Kalman Filter** fuses multiple noisy sensor measurements into a single best-estimate state by:

1. **Predicting** where the robot probably is based on the previous state + physics
2. **Correcting** that prediction with each new sensor measurement, weighted by how much we trust that sensor (its covariance)

The result is published as `/odometry/filtered` — a smooth, low-drift odometry estimate in the `odom` frame.

The `odom` → `map` transform (correcting for accumulated drift) is what AMCL provides. AMCL does not replace the EKF; it *corrects* the frame that the EKF works in.

### ekf_config.yaml — parameter-by-parameter

```yaml
ekf_filter_node:
  ros__parameters:
```

#### Coordinate frames

| Parameter | Value | Why |
|-----------|-------|-----|
| `map_frame` | `map` | Global fixed frame. |
| `odom_frame` | `odom` | Continuous (no jumps) frame. EKF publishes into this. |
| `base_link_frame` | `base_link` | Robot body. |
| `world_frame` | `odom` | Set to `odom` (not `map`) so the EKF maintains continuous odometry without AMCL jumps polluting the filter. |

**Why `world_frame: odom` and not `map`?** If you set it to `map`, the EKF tries to incorporate AMCL's pose corrections directly, which introduces discontinuities (the robot "teleports" slightly each time AMCL corrects). The standard nav2 pattern is: EKF lives in `odom`, AMCL publishes the `odom → map` TF, nav2 then uses `map` for planning. The two work in separate layers.

#### Sensor inputs

| Parameter | Value | What it is |
|-----------|-------|-----------|
| `odom0` | `/mirte_base_controller/odom` | Wheel odometry from Mirte's motor controller |
| `imu0` | `/io/imu/movement/data` | IMU on Mirte (accelerometer + gyro) |

#### odom0_config — what we extract from wheel odometry

The config is a 15-element boolean array selecting which of the 15 state variables to use from this sensor:

```
[x,     y,     z,                      ← position
 roll,  pitch, yaw,                    ← orientation
 vx,    vy,    vz,                     ← linear velocity
 vroll, vpitch, vyaw,                  ← angular velocity
 ax,    ay,    az]                     ← linear acceleration
```

Our setting: `[F,F,F, F,F,F, T,T,F, F,F,T, F,F,F]`

We take `vx`, `vy`, and `vyaw` from wheel odometry — the velocities. We ignore absolute position (it drifts) and ignore z/roll/pitch (Mirte is a 2D ground robot). We ignore acceleration (odometry doesn't measure it directly).

`odom0_relative: false` — measurements are in the absolute `odom` frame, not relative to the previous measurement.

#### imu0_config — what we extract from the IMU

Our setting: `[F,F,F, F,F,F, F,F,F, F,F,T, F,F,F]`

We take only `vyaw` (yaw rate) from the IMU. The IMU's gyroscope gives us a direct, noise-reduced measurement of angular velocity that is more accurate than what can be inferred from wheel speeds (especially when one wheel slips).

We deliberately ignore IMU acceleration (`ax`, `ay`) and absolute orientation (`roll`, `pitch`, `yaw`) because:
- Mirte's cheap IMU has significant yaw drift over time
- Absolute orientation from the IMU would fight with the wheel odometry's orientation
- Only the *rate* is reliable short-term

`imu0_relative: true` — IMU measurements are treated as deltas, not absolute world-frame values. This avoids needing a perfect heading reference at startup.

`imu0_remove_gravitational_acceleration: true` — subtracts the 9.81 m/s² gravity component from accelerometer readings (not used here but good practice for correctness).

#### Filter tuning

| Parameter | Value | Why |
|-----------|-------|-----|
| `frequency` | 5.0 Hz | How often the EKF publishes. Mirte's odometry comes at ~10 Hz and IMU at ~50 Hz; 5 Hz output is a good rate for nav2 without overloading the ARM CPU. |

#### Process noise covariance (Q matrix)

This 6×6 diagonal matrix tells the filter how much the robot's state can change unpredictably between updates — essentially "how much do we trust the physics model vs the sensors?"

```
[0.05, 0,    0,    0,    0,    0,
 0,    0.05, 0,    0,    0,    0,
 0,    0,    0.06, 0,    0,    0,
 0,    0,    0,    0.03, 0,    0,
 0,    0,    0,    0,    0.03, 0,
 0,    0,    0,    0,    0,    0.06]
```

The diagonal entries correspond to: `[x, y, z, roll, pitch, yaw]` process uncertainty.

| State | Value | Reasoning |
|-------|-------|-----------|
| x, y | 0.05 | Moderate positional noise — the robot can drift ±5 cm unpredictably per second due to slip and carpet. |
| z | 0.06 | Slightly higher — we don't control Z at all on a ground robot, so we let the filter know Z is uncertain. |
| roll, pitch | 0.03 | Lower — Mirte rolls and pitches very little on flat lab floors. |
| yaw | 0.06 | Higher — heading uncertainty is the biggest source of odometry error; being generous here lets the IMU correction have more influence. |

All off-diagonal entries are 0 — we assume the noise in each axis is independent. This is a simplification but reasonable for a ground robot.

## Sensor fusion architecture (HybridLocaliser)

The `hybrid_localiser` node merges up to three pose sources into `/robot_pose`:

### Sources

| Topic | Type | Source |
|-------|------|--------|
| `/amcl_pose` | `PoseWithCovarianceStamped` | AMCL — map-based, highly accurate when converged |
| `/rtabmap/localization_pose` | `PoseWithCovarianceStamped` | RTAB-Map — visual SLAM, optional |
| `/odometry/filtered` | `Odometry` | EKF output — continuous, no jumps, but drifts |

### Fusion strategy

Each source has a **weight** computed from its covariance:

```python
uncertainty = sqrt(abs(covariance[0]))  # x-position uncertainty in metres
weight = max(0.1, 1.0 - uncertainty * 2)
```

A source with `covariance[0] = 0.01` (1 cm uncertainty) gets weight `1.0 - 0.2 = 0.8`.  
A source with `covariance[0] = 0.5` (70 cm uncertainty) gets weight clamped to `0.1`.

Position is a weighted average of all available sources. Orientation is taken from the **most confident** source only (quaternion averaging is non-trivial and unnecessary here).

If no map source is available (AMCL not yet converged, RTAB not running), the node falls back to raw EKF odometry with a warning log.

The output `/robot_pose` is published at 10 Hz (timer at 0.1 s).

## Python nodes

### localisation_input_node.py

**Purpose:** Send an initial pose to AMCL so its particle filter starts converged rather than scattered.

**What it does:**
1. Subscribes to `/map` with `TRANSIENT_LOCAL` QoS (so it gets the map even if it started after the map server)
2. Once the map arrives, waits 2 seconds for AMCL to fully activate via the lifecycle manager
3. Publishes one `PoseWithCovarianceStamped` on `/initialpose` placing the robot at (0, 0, 0°)
4. Sets a covariance of 0.5 m in x/y and 0.1 rad in yaw — "we think we're at the origin but we're not certain to the centimetre"
5. Destroys its map subscription and goes idle

**Why covariance 0.5?** If we set it to 0 (perfectly certain), AMCL places all particles at exactly (0,0) and any small offset from the true starting position causes immediate localisation failure. Setting 0.5 spreads particles over roughly a 1 m radius, giving AMCL room to find the true pose on the first few scans.

### localisation_output_node.py

**Purpose:** Read AMCL's pose estimate and make it available to the rest of the system.

Subscribes to `/amcl_pose` with `TRANSIENT_LOCAL RELIABLE` QoS (matching AMCL's publisher). Exposes `get_position()` returning `(x, y, yaw_radians)` which other nodes can import and call.

The quaternion-to-yaw conversion uses the standard formula extracting the Z-axis rotation:
```python
yaw = atan2(2*(w*z + x*y), 1 - 2*(y² + z²))
```

### apriltag_corrector_at.py

**Purpose:** Correct AMCL's accumulated drift whenever the camera sees a known AprilTag.

**How it works:**

The robot's sorting area has AprilTags at fixed, known positions — every station and every dropbox has one. Those positions are stored in `semantic_map.yaml` (on the robot) as `(x, y, yaw)` in the map frame. The corrector node reads that file at startup and builds a lookup table of `{tag_id → world_pose}`.

At runtime it polls the TF tree at 5 Hz. When `apriltag_ros` detects a tag, it publishes a TF transform `camera_optical_frame → tag36h11:<id>`. The corrector grabs that transform (tag pose relative to camera), combines it with the tag's known world pose, and inverts the geometry to recover where the robot must be in the world frame.

The 2-D SE(2) chain:

```
robot_world = tag_world  ⊕  inv(cam→tag TF)  ⊕  inv(base_link→camera TF)
```

Where `⊕` is 2-D pose composition and `inv()` is the SE(2) inverse:
```
inv(x, y, θ) = (−x·cos θ − y·sin θ,  x·sin θ − y·cos θ,  −θ)
```

The result is published to `/initialpose` with a covariance that tightens as the robot gets closer to the tag:

| Distance | xy covariance | yaw covariance |
|----------|--------------|---------------|
| 0.3 m | 0.009 m² (~9 cm) | 0.015 rad² |
| 1.0 m | 0.030 m² (~17 cm) | 0.050 rad² |
| 1.5 m | 0.045 m² (~21 cm) | 0.075 rad² |

AMCL interprets a tight-covariance `/initialpose` as a high-confidence correction — it collapses the particle cloud around the new estimate immediately. Tracking then continues from that corrected point even after the tag leaves the camera.

A 3-second cooldown between corrections prevents spamming `/initialpose` while AMCL is still converging.

**Parameters set in localisation_launch.py:**

| Parameter | Default | What to change |
|-----------|---------|----------------|
| `semantic_map_path` | `''` (empty) | Pass via `semantic_map:=` launch arg |
| `tag_frame_prefix` | `tag36h11:` | Match whatever `apriltag_ros` uses — check with `ros2 topic echo /tf` |
| `camera_frame` | `camera_optical_frame` | Must match your camera's optical frame in TF |
| `base_frame` | `base_link` | Robot body frame |
| `correction_cooldown` | `3.0 s` | Lower if you want faster corrections, higher if AMCL overshoots |
| `max_detection_distance` | `1.5 m` | Ignore detections beyond this — accuracy degrades at range |

**semantic_map.yaml format expected:**

```yaml
stations:
  station_1:
    frame: map
    pose:
      x: 1.20
      y: 0.80
      yaw: 0.0
    samples: 50
    tag_id: 3

drop_boxes:
  dropbox_2:
    dropbox_2_tag:
      pose:
        x: 2.50
        y: 1.10
        yaw: 1.5708
      samples: 50
      tag_id: 7
```

The parser recurses through any nesting depth so both the flat (stations) and nested (drop_boxes) layouts are handled automatically.

### rtab_room_map.py

A standalone (non-ROS) OpenCV script for building a visual keyframe map using ORB features. Used for prototyping — not part of the main launch. Has two modes:

- `MODE = 'map'` — press S to save keyframes, F to finish and write `room_map.pkl`
- `MODE = 'localise'` — loads the saved map and matches the live camera feed to keyframes to estimate which room position the robot is at

This was used to validate the visual SLAM concept before integrating RTAB-Map.

### rtabmap_launch.py

Optional secondary launch for RTAB-Map visual SLAM. Subscribe to:
- `/camera/depth/image_raw` + `/camera/color/image_raw` + `/camera/color/camera_info` (Intel RealSense or similar depth camera)
- `/scan` (lidar)
- `/odometry/filtered` (EKF output — remapped from `odom` to this topic)

Publishes `/rtabmap/localization_pose` which the hybrid localiser subscribes to.

The `rtabmapviz` node is commented out since Mirte runs headless in the lab.

**ARM CPU optimisations applied:**
- `RGBD/NeighborLinkRefining: false` — disables ICP refinement between graph nodes (very expensive)
- `RGBD/ProximityBySpace: false` — disables proximity detection by spatial distance (expensive graph search)
- `Grid/FromDepth: true` + `Grid/RangeMax: 4.0` — limit the 3D occupancy grid to 4 m range to reduce memory and CPU

Before the first localisation run, confirm what frame names `apriltag_ros` publishes for your tags. On the robot, with the camera running and a tag visible:

| Topic | Type | Direction | Publisher | Subscribers |
|-------|------|-----------|-----------|-------------|
| `/map` | `OccupancyGrid` | out | `map_server` | AMCL, input_node |
| `/initialpose` | `PoseWithCovarianceStamped` | in | `input_node` (startup), `apriltag_corrector_at` (runtime) | AMCL |
| `/scan` | `LaserScan` | in (external) | lidar driver | AMCL |
| `/mirte_base_controller/odom` | `Odometry` | in (external) | motor controller | EKF |
| `/io/imu/movement/data` | `Imu` | in (external) | IMU driver | EKF |
| `/odometry/filtered` | `Odometry` | out | EKF | hybrid_localiser, RTAB-Map |
| `/amcl_pose` | `PoseWithCovarianceStamped` | out | AMCL | output_node, hybrid_localiser |

## Bugs fixed during development

### 1. YAML corruption in amcl_config.yaml

**Symptom:** AMCL crashed immediately on launch with a parameter type error. `/amcl_pose` was never published.

**Root cause:** Line 40 of `amcl_config.yaml` read:
```yaml
initial_pose_a: 0.0cd ~
```
A terminal command (`cd ~`) had been accidentally pasted into the config file. YAML parsed the value as a string `"0.0cd ~"` instead of a float, which nav2_amcl rejected at parameter load time.

**Fix:** Changed to:
```yaml
initial_pose_a: 0.0
```

### 2. QoS mismatch on /amcl_pose subscription

**Symptom:** AMCL was running and `/amcl_pose` appeared in `ros2 topic list`, but `localisation_output_node` and `hybrid_localiser` never received any messages. No error was printed — messages were silently dropped.

**Root cause:** `nav2_amcl` publishes `/amcl_pose` with `TRANSIENT_LOCAL + RELIABLE` QoS. This is equivalent to a "latched" topic in ROS1 — the last message is held in memory and delivered to any new subscriber immediately. Both our subscriber nodes used the default QoS (`VOLATILE + RELIABLE`). In ROS2, a `VOLATILE` subscriber is **incompatible** with a `TRANSIENT_LOCAL` publisher and receives nothing.

**Fix:** Added explicit QoS profiles to both subscriber nodes:
```python
_AMCL_QOS = QoSProfile(
    depth=1,
    durability=QoSDurabilityPolicy.TRANSIENT_LOCAL,
    reliability=QoSReliabilityPolicy.RELIABLE
)
```

## Known limitations and future work

- **`use_rtabmap` launch arg is not yet wired** to a conditional `IncludeLaunchDescription`. RTAB-Map must currently be started separately via `rtabmap_launch.py`.
- **The hybrid fuser's output covariance is not propagated.** A proper weighted-average fusion should update the output `PoseWithCovarianceStamped` covariance. Currently it is left zeroed — downstream nodes that rely on the covariance (e.g. a second EKF) will see incorrect uncertainty.
- **AprilTag corrector uses 2-D SE(2) geometry only.** Camera tilt and tag mounting height are ignored. This is accurate enough for a flat-floor ground robot but would fail if tags are mounted at steep angles.
- **IMU calibration.** The EKF's yaw accuracy is directly tied to IMU calibration. If heading drift is noticeable after ~30 seconds of driving, re-run the IMU calibration routine before the next run.
- **`tag_frame_prefix` must be set manually.** The default `tag36h11:` matches the standard `apriltag_ros` Humble package. If a different tag family or package is used the prefix must be updated in `localisation_launch.py`.
